## 审阅与范围选择

开始时工作区干净；项目及祖先目录、项目内未发现适用的 AGENTS.md。已阅读 README、Dockerfile、依赖列表、数据库迁移入口、Gunicorn 配置、现有备份上传和 COS 测试，以及鉴权/身份相关测试。

| 区域 | 依赖与边界 |
| --- | --- |

| 鉴权与权限 | before_request 校验令牌、强制改密、代入身份及请求中的操作人；`require_management_user` 判断管理权限；业务查询另有片区/站点/检查表和待审核可见范围 |

| 巡检业务 | 登记、问题、审核、验收、整改/复核、申诉、计划及流转记录相互依赖；首批不拆 |

| 备份 | JSON 配置、频率计算、pg_dump/psql、ZIP、storage 清理、COS 保留策略、手动接口和定时任务共用路径与锁 |
| 后台执行 | 首次请求惰性启动备份调度循环；该循环也清理问题/报告导出。Gunicorn 的 `post_worker_init` 另启动质安时限 worker；报告及专家问答有独立任务机制 |

导入 `app` 既有副作用包括：校验环境、创建存储目录、设置日志过滤器、初始化扩展及注册路由；SQLAlchemy 初始化不等于打开数据库连接。专家问答导入时创建线程池对象，但线程在提交任务时才启动。备份调度由请求钩子启动，不应移到新模块导入或构造函数中。已有部分模块使用整体命名空间注册，本批保留这些旧调用，但新模块不沿用此模式。

完整备份模块涉及数据库重建、文件删除和调度，不作为首批整体迁移对象。本批仅提取两个手动传输接口的 HTTP 适配与任务编排；数据库/文件恢复实现、COS、配置读写、调度器、锁创建、初始化和全部其他接口不变。

## 新边界

```text
app.py 原 URL 与 endpoint
  -> _backup_transfer_endpoints()：逐项显式注入现有函数及同一把锁
  -> backups/http.py：请求读取、manage_backups 授权、连接生命周期、响应/错误映射
  -> backups/transfers.py：任务互斥、调用原归档/恢复操作、更新任务配置
  -> 原 create_full_backup_archive / restore_full_backup_archive / 配置读写
```

`backups/__init__.py` 无初始化动作。两个服务对象的构造不进行 I/O，不创建锁或线程，不导入 `app`，不接收 globals/整个命名空间，不新增数据访问层或依赖。`app.py` 是组合点，每个请求获得轻量适配对象，但引用的是既有 `backup_job_lock`，自动和手动任务的进程内互斥关系不变。

没有使用 Blueprint：本批保留原注册位置、endpoint 名称和直接调用入口，尤其 `PlatformRequest.max_content_length` 依赖 `import_management_full_backup` 这个精确名称。后续是否使用 Blueprint，应先审计此类 endpoint 依赖。

## 兼容契约

| 接口 | 保持的行为 |
| --- | --- |
| `POST /api/management/backups/export` | 原 JSON 参数、身份和管理权限；ZIP 下载名、MIME、X-Backup-Path/Size、X-COS-Backup-Status/Key、Cache-Control 保持不变 |
| `POST /api/management/backups/import` | 原 multipart `file` 字段、无全局大小限制的 endpoint、权限、成功消息、manifest 和错误映射保持不变 |
| GET 备份概况、PUT 备份配置 | 本批未改实现；频率、保存/清理顺序和响应不变 |

两个接口的 401/403/404/409/500 语义保持；导入校验异常仍为 400，导出中的 ValueError 仍按原行为返回 500。COS 上传失败仍可成功下载本地 ZIP，并把配置标为 warning，不改为 HTTP 失败。

执行顺序必须保留：

1. 导出：读取请求参数 → 打开授权连接 → 检查 `manage_backups` → 关闭游标/连接 → 非阻塞获取原锁 → 读取配置 → 创建归档（其内部顺序不动）→ 锁内写配置 → finally 释放锁 → send_file。
2. 导入：打开授权连接 → 检查 `manage_backups` → 关闭游标/连接 → 非阻塞获取原锁 → 读取上传文件并调用原恢复函数 → finally 释放锁 → 读取/更新配置 → JSON 响应。
3. 锁忙时仍返回原 409，不在该端点中解析上传文件或开始操作。公共鉴权中间件仍可能为身份核对提前读取 request.form，本批未修改这一既有行为。
4. 不新增 commit/rollback。原连接关闭导致未提交事务回滚；任务运行前连接已关闭。任务失败不尝试“补偿恢复”，也不改文件和数据库的既有先后关系。

备份管理原本是管理权限控制的完整备份，不是按站点导出的备份；本批不新增或放宽该权限。全局登录、代入身份、操作人标记、文件访问鉴权、其他业务数据范围及审计机制均不改动。

## 独立记录的风险与后续

- **跨 Gunicorn worker 并发**：默认四 worker，各自有进程内 `threading.Lock` 和调度启动标记，不能阻止不同进程重复执行备份或与恢复互相干扰。本批不修复、不改变启动频率或锁类型。应单独设计数据库/文件级跨进程互斥及调度归属，再覆盖多进程争用、worker 异常退出、恢复期和失败重试；这是功能修复，不应混入结构调整。
- **配置与清理竞争**：JSON 配置原本直接写入，配置更新端点没有获取任务锁，且变更目标目录会清理旧目录；本批保持原样。需要单独评估原子写入与任务/配置更新互斥。
- **下载与恢复竞争**：原锁在 send_file 前释放，固定 latest.zip 的发布或 storage 清理可能与下载竞争。本批没有延长锁范围，以免静默改变调度行为。
- **恢复非整体原子**：数据库恢复与 storage 恢复不是一个共同事务，中途失败可能造成部分恢复；本批既不执行真实恢复，也不引入补偿策略。

下一批建议先提取备份配置规范化与时间计算，保留现有频率算法及文件写入行为；或在当前 COS 契约测试基础上单独拆分云存储适配。完整恢复和调度器应等各自故障/并发测试完善后再拆。应用工厂与旧整体命名空间注册的消除不属于本批。
