# 业务督导中心数智管理平台

本项目是一套面向业务督导、站点整改和管理分析的综合平台。系统以巡检业务为主线，同时提供考核、站点主数据、数据备份、系统安全和 AI 分析等能力。

> 本文档以当前代码中的实际逻辑为准，重点说明巡检系统的功能和状态流转。

## 服务器部署

在服务器项目根目录执行 `bash deploy.sh`（也可执行 `./deploy.sh`），一次完成前端和后端更新，无需分别运行旧脚本。脚本只拉取一次代码（仅允许快进），加载服务器 `.env` 并检查生产配置，然后依次构建发布前端到 `/var/www/ywddzx`、移除不再需要的 Vite 开发容器、重建后端、等待迁移及 Gunicorn 启动、验证运行时数据库结构。兼容 `docker compose` 和旧版 `docker-compose`；前端使用 `npm ci --include=dev` 按锁文件安装构建依赖，后端版本从 `frontend/package.json` 读取并覆盖过时的环境值。

运行账号需要项目目录、Docker及 `/var/www/ywddzx` 的操作权限。服务器须配置 `APP_SECRET_KEY`、`DB_PASSWORD`、`WEBAUTHN_RP_ID`、`WEBAUTHN_ORIGIN` 和 `CORS_ALLOWED_ORIGINS`，且 Nginx 已加载 `deploy/nginx/ywddzx-cache.conf` 与 `ywddzx-security.conf`。配置或构建失败时不会替换前端文件；后续步骤失败会停止并说明阶段，不自动回滚已完成的部署。此脚本会实际更新生产服务并执行迁移，请仅在准备部署时运行。

已经应用到数据库的迁移版本不能随未提交的功能代码一起删除，否则后端会在迁移阶段退出并循环重启，前端可能只显示Passkey暂不可用。`20261024_001` 是已撤销HTML原型的兼容节点：不新建、删除或使用原型表，只保留可解析的版本链；已有该版本的本地备份可以正常升级，未运行过原型的数据库也不需要创建其表。不得通过删除Passkey或随意修改数据库版本号来绕过启动错误。

大模型 Key 必须进入后端容器，仅在 SSH 交互终端里 `export` 不代表 Docker 已收到。部署会保留当前部署环境及项目 `.env` 的四个厂家 Key，对缺失项依次读取专用配置文件 `AI_KEYS_ENV_FILE`（默认 `/etc/ywddzx/ai.env`）、`/etc/environment` 及部署账号的 Shell 配置（兼容旧 `.bashrc`、`.zshrc` 等）。只读取 `DEEPSEEK_API_KEY`、`ZHIPU_API_KEY`、`DASHSCOPE_API_KEY`、`MIMO_API_KEY` 的单行固定值赋值，不执行配置中的命令、变量展开或 Shell 启动逻辑；专用文件应由部署账号保管并设为 `0600`，不要提交 Git。未配置的厂家保持可选，不影响其他厂家。部署日志仅显示是否配置及配置来源，不显示值；密钥只在重建后端的 Compose 子进程中补入，不额外传给前端构建。部署结束还会从后端实际环境核对四个厂家状态，页面的“Key 已配置”仍不代表余额、模型授权或网络可用。

## v11.3 统一照片上传与完整画面

巡检登记（含亮点）和提交复核共同使用 `InspectionPhotoUpload.vue`，同一套文件选择、手机拍照、剪贴板粘贴、桌面拖入、最多三张自动拼接、单张移除、继续添加、图片编辑与放大预览功能。编辑支持裁剪缩放、位置调换、圆形/矩形标注及线宽调整。新增图片按顺序处理，关闭、清空及切换问题会取消旧的异步结果；处理和编辑时不能提交。

新拼接布局默认等比完整显示，不再用铺满裁切方式丢弃画面边缘，缩略图也完整显示；用户主动缩放裁剪仍生效。旧编辑布局未指定适配方式时保留原有裁剪语义。提交仍是一张压缩后的JPEG，后端接口与照片必填/选填规则不变。登记草稿保留最终照片，不保留拼接前各原图的编辑状态。

## v11.2 人员编组与执行保护

今日外勤组有站点派工但尚未开工时允许调入、调出组员。组员在派工之后，为分派站点、对应检查表创建巡检记录，或给复用的月度巡检记录新增问题，整组即锁定。核对创建时间及当前派工成员，不以“已有计划”、非本组人员的记录、非任务站点/检查表或派工前的记录锁组；此锁定实时生效，与17:00的档期实绩展示窗口分离。已派站的带队人须先撤下派工再改变带队关系，已有视频派工人员仍按个人锁定，其他内勤人员可调整。

采用成员调整时，沿用同一排班事务锁，同步季度现场和年度计量计划中的成员、个人任务及待选区。计划中仍保留原带队组、站点和日期；旧任务撤销并保留成员快照，新任务另存，不改写实际记录。保存以短事务的记录表共享锁防止巡检写入与实绩校验交叉，沿用3秒锁等待及10秒语句超时；版本、档期、准驾证或审计异常均回滚。

“当前生效的今日巡检安排”同时读取当日有空、账号匹配、没有站点派工且尚未在分组中的人员，显示为“有空待编组”。将没空改回有空后，无需重新随机分组，可拖动或点选加入已有外勤组或内勤视频组；管理人员仍不能加入另一管理人员带队的外勤组，可独立带队。预览与拖动不会自动保存，须采用方案才同步生效。下方v10.8、v10.6及更早章节的外勤“已派站即整组锁定”描述为历史规则，已由本节替代，排班表站点整行锁定规则不变。

## v11.1.1 站间路网数据库

现行智能排班只读取PostgreSQL中的完整路网批次，不会在浏览、预览或确认时请求高德。对所有有效坐标的站点建立 `n*(n-1)/2` 个站对；每对固定取ID较小站点到ID较大站点的一个采样方向，往返共用此估算，不假定双向路况差异。按用户选择采用高德批量驾车估算（`v3/distance type=1`，每批至多100起点），用于粗略安排，不等同于实时最优导航。仍先满足计量目标、再均衡片区，最后按数据库行车时间组合站点。

`driving_matrix_runs/pairs/state` 保存采集批次、进度及当前发布指针；新批次收齐后同事务整体发布，只保留最近两份完整站对明细，失败不覆盖旧批次，中断可按同一任务续采。`driving_matrix_previews` 保留30分钟、绑定操作人与日期的派工预览，确认时仍校验人员、实绩、目标和版本。已删除v11.1的按需联网与SQLite两小时路网缓存实现，旧缓存文件不再被使用；路网数据没有两小时失效或实时回源。

部署迁移 `20261025_002`，并由 `deploy/install_driving_timer.py` 安装独立的 `ywddzx-driving-refresh.service/.timer`，北京时间每周一09:30运行，`Persistent=true` 可补执行停机错过的周期。部署提交一次后台初始化/补漏请求，CLI通过PostgreSQL会话级锁与已完成周期判断防止重复采集，不在Gunicorn中启动采集线程，不要求用户保持网页打开。采集按批提交、限速、不持有业务事务或排班锁。采集遇到网络/额度问题时记录失败并保留已收集部分，后台间隔10分钟有限重试，1小时内最多启动3次；运维可用 `systemctl start ywddzx-driving-refresh.service` 续采，页面不提供修改或触发按钮。

排班系统的“路网数据”位于“排班地图”下方，仅GET读取；原网址 `/management/driving-matrix` 和显示开关键保留，独立 `view_driving_matrix` 权限默认仅root，可通过角色模板/个人权限分配。展示采集进度、有效站点、已发布站对、成功批次及下次更新时间；站间明细按页查询，支持任一端站名的部分名称搜索、可达情况及行车用时/行驶距离双向排序，未应用条件与当前结果分开呈现。不可达不代表0分钟。新站或坐标变更等待下次周更新，不在排班中补查；失败或中断时原有效批次仍可用。高德Web服务Key继续使用 `AMAP_WEB_SERVICE_KEY` / `AMAP_KEY`，不写入业务表或前端。

## v11.1 驾车时间优先智能排班（历史实现，已由v11.1.1替代）

现场智能排班继续先补当月计量年度目标、再均衡片区季度覆盖率，在这些约束下按高德预计驾车秒数组合站点，时间相同时再比较驾车米数，替代v10.1的直线距离聚类。采用容量约束的启发式组合与有限交换，不承诺全局最优；组内最多10站用有向道路矩阵求最短行车时间的开放路径，不增加办公室绕行目标。预览显示检查顺序、站间预计分钟、行驶公里及逐段行车信息，单站无站间行程，视频派工和已有实绩不改动。

后端使用高德 `https://restapi.amap.com/v3/distance` 的 `type=1` 驾车矩阵，一批最多100个起点；不是`type=0`直线测量。以选中站点为目的地按需批量查询候选起点，使用实际返回的秒数、米数，区分双向道路，不将未查询或不可达路线当作0。`.schedule-driving/routes.sqlite3` 位于共享storage内，文件0600；按坐标和方向缓存最长2小时，不长期伪装实时路况。相同候选/目标/人员容量复用已计算方案，单机多Gunicorn进程通过文件锁避免重复计算，间隔限流、65秒查询预算；首次数据量较大可再次计算继续使用已缓存结果。不新增后台任务、依赖或业务数据库迁移。

高德查询在业务连接关闭后执行，不持有全局排班锁。确认派工不访问高德，使用绑定操作人、日期、原预览token且有效30分钟的路线快照，并在原调度事务内重查坐标、人员档期、实绩、计量目标、准驾证、排班及配额版本。发生变化要求重新预览，失败全部回滚原排班；高德Key缺失、额度不足或路径异常时明确提示，不退回直线距离或伪造方案。缓存可清理重建，但请勿在正在计算/确认时操作其文件。

高德浏览器地图Key与Web服务Key平台类型不同，后端配置 `AMAP_WEB_SERVICE_KEY`（Web服务类型），兼容服务器现有的 `AMAP_KEY` 别名。可在项目 `.env` 或 `/etc/ywddzx/amap.env` 设置，后者建议0600；也支持 `AMAP_KEYS_ENV_FILE` 指定文件，并安全读取部署账号 `.bashrc` 等既有配置。部署只读取固定值，不执行Shell配置代码、不输出密钥，不注入前端；未配置不影响站点地图和手动排班，但多站现场智能组合会提示配置，不能用浏览器Key冒充。高德服务额度、IP白名单和计费以实际账号为准。

下文v10.x中本地直线聚类、不依赖在线地图的说明为历史实现，现行现场智能组合以本节v11.1为准；历史派工和巡检实绩不追溯重算。

## v11.0 全局显示开关与月度站点评分

桌面界面采用80%的紧凑显示密度：Vite沿用现有PostCSS流水线，对字号、间距、按钮、表格和响应式断点中的固定像素尺寸统一换算。不是对DOM使用zoom/transform，不修改浏览器缩放，地图、画布、拖拽坐标和视口高度保持原坐标体系。768px及以下移动端、打印和独立HTML报告保留原尺寸；导出HTML时识别并移除紧凑分支、还原文档响应式规则，PPT文件不受影响。公共比例与分支标识位于 `frontend/src/utils/uiDensity.js`，转换在 `frontend/build/desktopDensity.js`，不引入新的运行时依赖。

HTML阅读修复：财务分类共用带显式配色、实际占比和零值处理的统计组件，卡片不再强行拉齐高度。设备设施从成稿的 `equipment_analysis` 读取高频原因、特性和重点问题，按保存片区顺序展示全部受检站点，不再依赖新模板不生成的旧分析字段；保留旧成稿的兼容展示。非油增加概览指标、可展开的片区/类别明细及完整原文说明，统计、图片和原因均来自成稿，展开与导出不重新取实时配置或调用AI；HTML导出展开所有正文，PPT生成逻辑不变。

报告后台线程通过共享storage下的 `.report-job-locks` 文件占用锁标识存活（部署的单机多Gunicorn进程环境）。任务认领使用数据库条件更新，重复线程不能再次认领同一任务；读取生成状态或准备新任务时，仅将超过3分钟无更新、且没有存活占用者的任务记录为“已中断”。长时间AI请求仍持有锁，不按固定时长误判；状态修正保留原进度、最后成功成稿和AI缓存，不自动发起收费重试、不新增定时扫描。占用文件不能在任务运行中删除；该机制不替代跨主机队列或自动续跑。

报告生成的查看权限拆分为“督导中心视角”（兼容原 `view_inspection_reports`）和“处室部门视角”（`view_department_inspection_reports`）。督导中心保留完整工作台，生成仍需 `generate_inspection_reports`；处室视角默认HTML阅读，可切换PPT并导出，不展示共享配置、生成操作日志或生成操作。处室只按月份选择历史成稿，未生成或不可读取的月份置灰；按保存的 `report_month` 归档，同月多份成稿取最后成功生成且兼容当前报告的数据，不把跨月自定义日期范围自动拆成多个月。首次打开显示最后成功成稿所属月份，切换类型重新读取该类型的可用月份，不修改任何配置、不调用AI；不覆盖督导中心原有的PPT/HTML偏好。质安部对应质量计量与安全质量，发展计划部对应设备设施，油气事业部对应现场服务，非油事业部对应非油，财务部对应财务。两种视角同时授权时使用督导中心视角；处室权限对其他角色不生效，不改变巡检业务页的数据范围。

部署迁移 `20261025_001` 将五类处室现有角色及个人的旧查看授权/拒绝迁移为处室视角，并关闭其旧督导中心授权，保留个人拒绝、其他角色和片区/检查表绑定；迁移不会给原先无查看权限的账号新增授权。菜单、路由、成稿读取、PPT导出、任务状态、预览及下载均校验相同权限；配置与AI生成接口仅允许督导中心。HTML模式的“导出HTML”直接下载当前成稿的独立文件，内含样式与图片；PPT模式仍走原PPT导出。HTML导出不调用AI、不读取当前配置，图片请求复用且最多并发4个，读取失败明确报错，不输出缺图文件；不执行脚本或加载外部资源。

页面显示管理新增 `manage_page_visibility` 独立权限，默认仅root启用，允许分配给其他角色或账号。菜单、路由、管理API统一校验该权限，不再依赖用户管理权限。开关修改只提交变化项，立即保存至共享配置，失败还原；一键全部显示也直接保存。配置不改变业务数据权限，隐藏页对所有账号的菜单生效；有权限的用户始终可以进入显示管理恢复页面，管理入口不参与自身隐藏。在线且可见的窗口每30秒核对全局显示配置，重新聚焦立即核对；读取失败保留上次成功配置，旧请求不能覆盖刚保存的配置。修改人与开关变更写入安全审计，同事务失败回滚。

站点评分改用月份选择器，默认上海时间上一个自然月。评分读取、人工调整和导出统一使用 `YYYY-MM`；兼容旧客户端传入完整自然月的起止日期，不再接受逐日或跨月评分范围，人员出勤的日期范围不变。仅启用且存在 `is_scorable` 字段的检查表可用，扣分仍只使用审核通过的问题，同规范只扣一次。保持既有等权评分及人工调整记录。前端仅读取选中检查表的台账，切换条件取消旧请求；明细可按规范ID、内容、问题描述及扣分/调整状态筛选，导出与调整弹窗保存打开时的月份快照。

## v10.9 视频巡检整站异常免检

被分配月度视频任务的用户可从右上角“今日安排 → 我的巡检待办”按站点击“报告视频异常”，填写1至500字的必填原因。确认后，该站本月安全、计量、现场三张视频检查表统一异常免检，不再计入个人待完成或历史视频未完成。今日卡片保留异常状态和原因；历史任务退出待完成分类，原始任务和留痕不删除。仅适用于普通月度视频任务，不影响现场、年度计量及其他月份。

视频排班整站置灰，原因直接显示，详情可看登记人、时间及原派工。异常免检不算实际检查完成，不虚构巡检记录；已有部分实绩仍独立保留。异常站点整行锁定，不能改派、清空或被智能方案替换；人员档期的原派工追溯也展示异常原因，不凭免检生成实绩。

巡检登记的人工引用顺序为“实际问题描述 → 搜索选择规范 → 问题照片”。描述填好后，用户主动点击“查找相似规范（不调用AI）”，不按输入停顿自动请求，避免中文输入法、临时停顿触发无效查询。手动搜索一直可用，不依赖检索完成；候选不会自动选中或替换用户的选择。

`POST /api/inspection-standards/history-recommend` 仅走本地已审核历史检索，不会调用AI或在失败后回退到AI。沿用v7.4权限范围和有效规范过滤、内容缓存失效规则，只返回描述相似度至少0.55的前6个不同规范；相似度不是正确率，仍须人工核对。输入变化、切换引用方式或离开页面会取消旧请求并阻止过期响应回填，人工已选规范不会因修改描述而自动更换。

搜索下拉框、AI候选和历史候选共用展示组件：规范ID、检查表名称、后端根据 `is_register_visible` 投影的 `register_display_text`。全部字段关闭时显示“未设置登记展示字段”，不回退到隐藏字段生成标题或摘要；选定规范后的完整详情仍可核查。无需数据库迁移或新依赖。

## v7.4 历史问题增强规范引用

巡检登记的AI引用规范在v7.3本地规范检索基础上，加入已审核问题的“实际问题描述 → 规范ID”关联。历史取数沿用当前登录用户在巡检问题列表的站点、片区、检查表与人员范围，只使用审核通过、非申诉中、非已销毁且引用当前有效规范的问题。外部模式使用外部规范ID，内部模式使用问题实际保存的内部规范ID，不猜测关联、不修改历史问题。

- 相似描述：中文n-gram TF-IDF余弦检索历史问题，重复描述去重，按规范取最高相似度，避免大量重复记录挤占候选；与规范BM25结果通过加权RRF融合，保留两路候选名额。发送给AI的仍只有当前问题与有限的规范原文，不发送历史问题原文、站名或问题ID。
- 可靠重复：规范化后描述完全一致、至少3个站点及3次巡检引用同一有效规范、没有引用分歧，且当前规范原文检索排名前5并有至少3个共同词片段时，直接返回历史推荐，不调用AI。短描述和宽泛“其他”条款不走此通道。数字、负号、否定词及数字之间的空格保留，推荐依然必须人工确认，不自动登记。
- 重复请求：相同描述、当前有效规范及完整可见历史未变化时，最多30分钟复用成功AI结果，单进程最多64份。只保留摘要键及推荐结果；失败或本地兜底不缓存。历史索引最多2份，按完整历史内容更新；审核反转、修改、删除、权限导致可见数据变化或规范停用后，下次请求不能命中旧资料。重启会清空进程缓存并从数据库重建；无需新依赖、模型下载或数据库迁移。
- 可追溯：界面区分“历史审核推荐”“AI历史推荐”和新AI推荐，已有AI使用记录保存实际是否调用、零调用费用及复用说明；服务日志增加历史数量、相似度、引用冲突、检索耗时及缓存命中指标，不记录历史问题原文。

只读回放：以较早5133条有效问题为历史，将较晚800条留作测试，不把测试问题本身放入历史。候选中找回原引用ID的比例从92.125%提升到98.625%，本地历史检索与融合平均约2.3ms（不含数据库、资料指纹和AI耗时）。严格免调用通道仅命中2条且与留出标签一致，样本很少，不代表整体推荐准确率或所有请求都能毫秒返回。新问题仍可能需要一次AI调用，历史人工引用仅是弱标签。

复测命令：在backend目录运行 `python tools/benchmark_standard_history.py`，只读、不调用AI、不输出问题原文。算法参考：[RRF官方说明](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)。

## v7.3 AI引用规范检索

登记AI引用规范改为本地词法RAG：中文二/三字词片段BM25与业务近义词扩展召回48条具体候选，额外保留最多12条宽泛条款，交给DeepSeek精排。不是向量检索，不需要新服务、模型下载或数据库扩展。大条款按查询相关窗口摘录，规范资料预算16000字符（非token）；界面仍返回完整规范详情，AI只能选择候选中的真实ID。

每次从当前有效规范生成内容指纹式缓存键，最多保留4份进程内索引。新增、编辑、停用、删除或恢复备份改变内容即重新索引，不以固定TTL导致停用规范继续推荐。内部规范关联已停用外部规范时，同样从候选排除；历史问题及报告分析不改动。

仅引用规范使用非思考模式、1800输出token预算、45秒请求超时且不自动重试；无词法依据时提示补充信息，AI异常时返回明确标为本地匹配的候选。报告生成的AI配置不变。算法仍可能漏召回语义差异较大的条款，需人工确认，不以“其他”兜底伪装成高置信度匹配。

本地回放1524条已审核、去重历史问题：原引用ID候选召回率约93.8%，平均资料量减少约89%，本地检索约1.25ms（不含数据库及AI耗时）。历史人工引用属于弱标签，含“其他”条款，因此该数值不是最终推荐准确率。可在backend目录运行 `python tools/benchmark_standard_retrieval.py` 重测；只读数据库、不调用AI、不输出问题原文。服务日志仅记录候选数量、资料字符量、检索耗时等指标。

参考：[DeepSeek非思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)、[检索与重排](https://www.elastic.co/docs/solutions/search/ranking)。本版本无新增数据库迁移，仍需先完成v7.2启停状态迁移。

同时保留备份恢复上传修复：仅 `/api/management/backups/import` 取消后端及Nginx大小限制，需加载 `deploy/nginx/ywddzx-security.conf` 才能解除代理层限制，其他上传限额不变。

## v7.2 外部规范启停

检查表数据管理的“维护规范数据”支持逐条启停。停用规范仍保留历史详情，但从登记候选和 AI 推荐中排除；关联停用外部规范的内部规范也不能用于新登记。服务端提交时再次校验，历史问题不做修改。

升级时需执行 Alembic 数据库升级至 `20260910_001`，新增 `external_standard_status` 状态表。迁移可重复执行，现有规范默认启用。请先完成数据库迁移再启动新后端；回退代码不会删除已保存的启停状态，但旧代码不执行停用限制，因此不应在回退后继续开放登记。

## 巡检系统

### 核心业务对象

| 对象 | 含义 | 关键关系 |
| --- | --- | --- |
| 站点 | 巡检和整改的业务主体 | 关联片区、站点账号、证照、计划和巡检记录 |
| 检查表 | 来自外部原件的结构化检查内容 | 每张表包含动态字段和多条外部规范 |
| 外部规范 | 由检查表原件拆解得到的规范 | 每条拥有全局唯一的外部规范 ID |
| 内部规范 | 业务督导中心归纳形成的巡检规范 | 一条内部规范可挂载多条外部规范 |
| 巡检记录 | 某站点在某个周期内对某张检查表的一次巡检载体 | 一条记录可包含多个问题和多名检查人 |
| 巡检问题 | 检查人引用规范后登记的实际问题 | 必须归属站点、检查表、外部规范、巡检记录和提交人 |
| 排班单元格 | 某张检查表在季度或月度周期内对某站点的计划 | 现场按外勤组、视频按单人整站安排；已有对应巡检记录即标黄锁定，不依赖审核或流程确认 |

### 规范体系与引用逻辑

```mermaid
flowchart LR
    PDF[PDF 检查表原件] --> TABLE[检查表]
    XLSX[可下载的原始表格] --> TABLE
    TABLE --> E1[外部规范 A]
    TABLE --> E2[外部规范 B]
    TABLE --> E3[外部规范 C]

    I[内部规范] -->|1 : N 挂载| E1
    I -->|1 : N 挂载| E2
    I --> TAG[标签群组与标签]

    E1 --> R1[对应检查表的问题记录]
    E2 --> R2[对应检查表的问题记录]
```

规范引用遵循以下原则：

1. 外部规范始终归属一张具体检查表，是问题进入巡检记录和报告统计的最终落点。
2. 一条内部规范可同时挂载多条外部规范，但一条外部规范不能同时归属多条内部规范。
3. 使用内部规范登记时，系统按挂载关系展开为对应的外部规范问题。一条内部规范挂载多条外部规范时，可在不同检查表记录下生成对应问题。
4. 问题列表同时展示内部与外部规范信息；巡检记录仍以外部规范和检查表为统计依据。
5. 系统可在管理端切换巡检登记使用内部规范还是外部规范。

### 巡检登记

巡检登记分为“发现问题”和“未发现问题”两种入口：

```mermaid
flowchart TD
    A[选择站点] --> B{是否发现问题}
    B -->|否| C[选择检查表]
    C --> D[创建或复用本周期巡检记录]
    D --> E[保存为无问题记录]

    B -->|是| F{规范来源模式}
    F -->|内部规范| G[人工或AI引用，可多选内部规范]
    F -->|外部规范| H[人工或AI引用，可多选外部规范]
    G --> I[按挂载关系展开外部规范，同批去重]
    H --> J[确定各外部规范和所属检查表]
    I --> K[共用一次填写的问题描述与照片]
    J --> K
    K --> L[校验全部目标，创建或复用对应巡检记录]
    L --> M[同一事务逐条保存独立问题，失败整体回滚]
```

登记阶段的主要规则：

1. 默认按“自然月”控制同站点、同检查表的巡检记录唯一周期；管理员可改为自然周、自然季度或自然年。
2. 在当前周期的记录尚未确认完成时，后续提交会继续进入同一条巡检记录，不会重复新建。
3. 记录确认完成后，当前周期不再允许新增问题；进入新周期后可创建新记录。
4. 同一条巡检记录可包含多名检查人。每条问题的检查人是实际提交该问题的账号，不会统一挂到第一名检查人。
5. 问题照片支持选择、拖拽和粘贴，最多选取 3 张后进行裁剪、位置调整、圆形或矩形标注和自动拼接；标注线宽可调，最终以一张合成图保存。提交复核也复用该图片编辑器。
6. 页面提供本地草稿自动保存和恢复，会话即将过期时会提前提示用户。
7. 已选清单可跨检查表多选规范，一次提交分别生成独立问题ID，审核、整改、复核及申诉仍按每条问题单独流转。生成条数取展开、去重后的外部规范数量。

## 巡检主流程

### 端到端流程图

```mermaid
flowchart TD
    REG[检查人巡检登记] --> REC[形成或更新巡检记录]
    REC --> MULTI[统计本表所有参与检查人]
    MULTI --> CONFIRM{所有检查人是否已确认}
    CONFIRM -->|否| WAIT[等待其他检查人确认]
    WAIT --> CONFIRM
    CONFIRM -->|是| COMPLETE[巡检记录确认完成并封存新增]
    AUTO[达到配置天数 / 后台确认] --> COMPLETE

    COMPLETE --> AUDIT[问题进入审核]
    AUDIT --> RULE{命中启用的自动审核规则}
    RULE -->|是| AUTO_RESULT[自动通过或否决]
    RULE -->|否| MANUAL[有权用户人工审核]
    AUTO_RESULT --> DECISION{审核结果}
    MANUAL --> DECISION

    DECISION -->|否决| DROP[已销毁：退出统计和整改流转<br/>保留问题与历史记录]
    DECISION -->|通过| ALLAUDIT{本表问题是否全部审核完成}
    ALLAUDIT -->|否| AUDIT
    ALLAUDIT -->|是| SIGN[对应站点账号进行站经理签名验收]

    SIGN --> HASISSUE{是否有审核通过的问题}
    HASISSUE -->|否| NORMAL[正常记录，签名验收完成]
    HASISSUE -->|是| RECTIFY[问题进入站点待整改]

    RECTIFY -->|指定五张表、申诉期内且从未申诉，填写理由| APPEAL[申诉中：暂停整改，进入申诉空间]
    APPEAL --> AREA{所属片区初审：原因必填}
    AREA -->|拒绝| RECTIFY
    AREA -->|通过| QUALITY{授权质安部终审：原因必填}
    QUALITY -->|拒绝| RECTIFY
    QUALITY -->|通过| DROP

    RECTIFY --> STATION_RESULT{站经理提交整改结果}
    STATION_RESULT -->|已整改| RPHOTO[整改说明 + 必传整改照片]
    RPHOTO --> REVIEW[进入督导组待复核]
    STATION_RESULT -->|站级无法整改| UNABLE_REVIEW[进入待复核，无需整改照片]
    UNABLE_REVIEW -->|通过站级无法整改| UNABLE_DONE[站级无法整改，终态，无需复核照片]
    UNABLE_REVIEW -->|驳回站级无法整改| BACKLOG

    REVIEW --> REVIEW_RESULT{督导组复核结论}
    REVIEW_RESULT -->|整改通过| CLOSED[已闭环<br/>必传复核照片]
    REVIEW_RESULT -->|整改不通过| RETURN[记录本轮复核退回<br/>复核照片和说明均选填]
    RETURN --> BACKLOG[恢复为站点待整改<br/>恢复站经理待办并展示退回提示]
    BACKLOG --> RECTIFY
```

记录确认与封存规则：

| 规则 | 系统行为 |
| --- | --- |
| 多人参与 | 任意一人确认只记录本人进度，必须所有参与检查人均确认后才算完成 |
| 自动确认 | 默认超过 7 天自动确认；管理员可设置 1-31 天或关闭自动确认 |
| 完成效果 | 封存当前周期的新增入口，然后才允许问题审核；不作为排班表已检查判定的前置条件 |
| 已有问题编辑 | 检查人确认完成本身不会取消已有问题的编辑权；问题审核后则需先重置为待审核才能继续编辑 |
| 流程重置 | 只有具备“重置巡检记录流程”权限的用户可操作，并会清除关联问题的审核结果 |
| 签名后限制 | 站经理签名验收后不允许再重置巡检记录流程 |
| 删除记录 | 删除巡检记录会级联删除该记录下的巡检问题，排班表下次核对时根据剩余记录展示实绩 |

### 问题审核状态

```mermaid
stateDiagram-v2
    [*] --> 待审核: 问题创建
    待审核 --> 审核通过: 人工或自动通过
    待审核 --> 审核否决: 人工或自动否决
    审核通过 --> 待审核: 重新判定
    审核否决 --> 待审核: 重新判定
```

1. 问题所属巡检记录尚未确认完成时，不允许审核。
2. 自动审核只使用唯一外部规范 ID 进行全匹配，所有规则平级，可分别配置自动通过或自动否决。
3. 审核否决的问题不参与巡检记录异常数量、整改复核流转和后续报告数据。
4. 审核否决时系统会取消该问题的“优秀问题”标记。
5. 问题一旦审核，提交人的通用编辑与删除权限暂停；审核人重置为待审核后才可再次编辑。

> v6.2 恢复站级无法整改申请和终态。此前 v6.1 已迁回待整改的问题不自动重新结案，需要站点重新提交申请并由督导复核。已销毁不是物理删除，可通过重新判定恢复。

问题流转记录遵循以下原则：

1. 登记、巡检完成确认、人工/自动审核及重新判定、签名及撤销、问题修改和状态调整均纳入流转记录。历史审核只补回数据库中仍存在的最后一次结论，不虚构早期事件。每次“提交整改”和“提交复核”都写入独立历史记录，保留轮次、操作人、时间、前后状态、结果、说明和照片。
2. “整改不通过”不是终态：问题从“待复核”恢复为“待整改”，重新出现在对应站点账号的待办中，并显示上一轮退回原因和退回时间。
3. 站点重新提交整改时进入下一轮“待复核”；当前复核展示字段会为新一轮清空，但上一轮结果、说明和照片（如有）继续保存在历史记录中。
4. 巡检记录只有在全部审核通过问题都“已闭环”或“站级无法整改”后，才完成整改跟踪；存在被退回或待复核问题时仍处于跟踪中。
5. “我的待整改 / 待复核”和“巡检问题列表”均可查看完整流转时间线，站点账号只能处理本站被退回的问题。

## 权限与数据范围

前端菜单隐藏只用于改善交互，最终安全判断由后端根据签名会话中的当前用户执行。

```mermaid
flowchart LR
    TOKEN[服务端签名 Token] --> USER[当前登录用户]
    USER --> PAGE[页面访问权限]
    USER --> ACTION[新增 / 编辑 / 删除 / 审核 / 导出等操作权限]
    USER --> SCOPE[数据范围]
    SCOPE --> OWN[本站数据]
    SCOPE --> REGION[指定片区数据]
    SCOPE --> ALL[全部站点数据]
    SCOPE --> TABLES[指定检查表范围]
```

权限原则：

1. `root` 拥有全部权限，其他角色使用“角色通用权限 + 用户个性化权限”的模式。
2. 用户存在个性化权限时，个性化权限优先于角色通用权限。
3. 本站、片区和全部站点是互斥的主数据范围，可叠加检查表范围限制。
4. 站点账号和片区账号默认不查看待审核问题，只在问题完成审核后进入其可见范围。
5. 检查人姓名和手机号可通过独立权限对特定角色隐藏。
6. 已闭环问题原则上不可修改或删除，只有 `root` 可在必要时使用管理权限处理。

## 数据一致性与追溯

1. 外部规范 ID 是规范的全局唯一标识，已被业务数据引用的规范不允许删除，但可修改内容并在关联页面中同步展示最新内容。
2. 巡检问题保留问题照片，以及每轮实际提交的整改/复核照片和对应时间；“整改不通过”可选填复核照片，提交后同样保留本轮照片供历史追溯。
3. 整改和复核采用追加历史记录，逐轮保留操作人、状态变化、结果、说明和照片，不会因复核退回或再次提交而丢失上一轮信息。
4. 删除问题会同步更新巡检记录结果和相关计划完成情况；删除巡检记录会级联删除其下问题。
5. AI 报告主要使用已确认完成的巡检记录和审核通过的问题，AI 生成内容在页面和导出结果中应带有明确标识。

### v6.9 待复核列表轻量加载

### v6.8 报告字体与翻页优化

六类PPT的正文、表格、图表、母版、主题和内嵌图表工作簿统一只声明微软雅黑（Microsoft YaHei）或宋体（SimSun）。兼容版本升级会重新准备旧成稿的文件与预览，不重新调用AI。移除导出弹窗重复创建入口，正常直接下载与预览一致的文件，仅失败时提供重试。

预览按报告实例缓存最多8页、24MB图片（单张当前页可超过上限），并预加载前1页、后2页，并发上限2。切换成稿或离开页面取消请求并释放URL，不持久保存账号私有图片；页面接口仍检查权限，后端仅验证所请求图片，不再每次遍历整份报告的图片文件。

**部署字体注意：** 微软字体文件不随仓库分发。管理员应将有合法使用授权的微软雅黑及宋体 `.ttf/.ttc` 放入 `storage/report_fonts`，Compose已挂载此目录，后端启动刷新字体缓存。缺少字体时Linux渲染器仍会使用系统替代字体，无法保证网页字形与WPS完全一致；应在部署时用 `fc-match 'Microsoft YaHei'` 和 `fc-match 'SimSun'` 核实匹配，避免误以为仅修改PPT字体声明就已安装字体。

### v6.7 报告PPT兼容性

六类报告统一通过 `backend/pptx_compatibility.py` 处理原生图表、数值缓存、坐标轴和字体。柱形/条形图下方使用独立可编辑的PPT表格，明确写入零值；不删除零值站点，不用非零小数冒充0。图表、内嵌工作簿、文字和表格仍可编辑，导出不是整页图片。

网页默认预览由最终导出的同一份PPT经容器内LibreOffice渲染，使用鉴权图片接口按页加载，不再独立拼装另一套HTML版式。首次准备需要转换时间，不调用AI；`report_ppt_artifacts.py` 按成稿内容、非油源PPT和兼容版本缓存，跨进程锁防止重复转换，转换串行执行避免并发占满资源，同一缓存文件用于预览和下载。导出任务仍按登录用户鉴权，成稿共享规则不变。派生缓存30天未使用后清理，不删除原始成稿；无需数据库迁移。

自动测试覆盖零值、小数、全零图表、可编辑工作簿、六类报告缓存及预览权限；容器内进行了实际渲染检查。不同办公软件仍可能因字体或图表引擎存在差异，旧版/企业版WPS需要在目标环境补充验收，不能保证像素级一致。

### v7.1 质安流程时限管理（取代 v6.6 共享审核时限）

仅适用计量稽查检查表（视频/现场）、环境无异味管理检查表（现场）、质量安全环保检查表（视频/现场）。root 通过“管理系统 → 质安流程时限管理”（`/management/quality-deadlines`）分别启用或关闭验收、申请、片区初审、质安部终审四项时限，调整工作小时数（1至8760的整数），两级审核分别选择超时处理方式。可按巡检记录ID、问题ID、事件类型筛选追溯日志；普通角色不能访问管理接口，身份以服务端当前登录用户为准。以下倒计时仅在对应开关启用时执行。

```mermaid
flowchart TD
    READY[检查人确认完成且全部问题审核结束] --> ACCEPT[站点验收，默认72工作小时]
    ACCEPT -->|期限内签名| SIGNED[人工签名验收]
    ACCEPT -->|到期| AUTO[系统自动验收，不伪造签名，记录待办理账号]
    SIGNED --> WINDOW[审核通过的问题进入待整改，申诉期默认72工作小时]
    AUTO --> WINDOW
    WINDOW -->|申请期内且从未申诉| AREA[片区初审，独立工作小时计时]
    WINDOW -->|申请期结束| RECTIFY[禁止新申诉，继续整改]
    AREA -->|初审通过| QUALITY[质安部终审，从接收起重新计时]
    AREA -->|拒绝| RECTIFY
    QUALITY -->|拒绝| RECTIFY
    QUALITY -->|通过| DESTROY[问题已销毁，历史保留]
    AREA -->|本阶段到期| AREA_RULE{片区规则快照}
    AREA_RULE -->|自动通过| QUALITY
    AREA_RULE -->|自动拒绝| RECTIFY
    AREA_RULE -->|等待人工| MANUAL[继续人工审核，不自动决策]
    QUALITY -->|本阶段到期| QUALITY_RULE{质安部规则快照}
    QUALITY_RULE -->|自动通过| DESTROY
    QUALITY_RULE -->|自动拒绝| RECTIFY
    QUALITY_RULE -->|等待人工| MANUAL
```

- 验收期限从“检查人确认完成且全部问题审核结束”的时刻起算，不从巡检登记日期倒推；有待审核问题不能自动验收。自动验收保留兼容的已验收状态，以独立来源字段区分，巡检记录支持筛选，所含问题均追加系统自动验收流转记录。
- 申诉申请期从验收后问题进入待整改开始（首次上线存量待办有宽限）。到期按钮置灰，后端同时拦截，包括在到期前打开弹窗、到期后提交。已经发起的申诉不受申请期结束影响；问题仍仅可申诉一次。
- 片区与质安部各自默认72工作小时，片区通过后质安部重新计时。超时默认等待人工；片区自动通过只转交终审，质安部自动通过才销毁问题，任一级自动拒绝均恢复整改。不冒用人员身份，两级先后超时分别保留处理时间、人员快照和生命周期记录。
- 四个开关分别确认、立即持久化。关闭某项解除该项已有待办限制，人工流程正常；重新启用给予该阶段未结束任务完整期限，已结束事件不重开。只调整小时数或处理方式不改变已开始任务的快照。
- 北京时间工作日全天24小时累计，普通周末和法定节假日暂停，国务院调休补班日计时；不是朝九晚五工时。`chinesecalendar==1.11.0` 提供2004–2026年官方安排，迁移写入 `quality_work_calendar`，计时在PostgreSQL函数中执行，无外部实时API依赖。前端共享缓存日历、每分钟更新显示，非工作日剩余小时不递减。
- 日历缺失年份不推测：无法计算的截止时间返回空，暂停自动判定及申请到期拦截，保留人工流程。管理页显示覆盖范围。下一年国务院安排公布后，更新并固定依赖版本，在后端执行 `python sync_quality_calendar.py` 补充日期；该命令可重复执行，不覆盖已有日历及历史证据。补齐后低频扫描继续计算待办。旧年份更正需要单独核查任务快照，不能直接覆盖生产日历。
- `quality_deadline_events` 保存配置人、规则版本、截止时间、自动处理时间、超时阶段、阶段接收人员和超时时有权限的账号。无可用账号也明确记录，供人工核查权限缺失与管理安排，日志不是自动认定某个人失职的结论。即使之后问题被删除，管理追溯信息仍保留。
- 部署先安装新依赖并迁移至 Alembic `20260909_002`。旧天数乘24转换为小时；旧审核开关及超时方式分别复制到两级。迁移为未结束任务提供升级时刻起的新完整期限，重复执行不重置自定义设置或宽限起点；历史时限、策略字段和日志不删除。Docker入口先迁移和验证结构，再用 Gunicorn `post_worker_init` 启动后台扫描。默认每180分钟唤醒，`QUALITY_DEADLINE_SCAN_MINUTES` 可调30至1440分钟；各实例保持一致。数据库事务锁与 `next_scan_at` 防止重复扫描，重启不清除调度时间，关闭功能跳过扫描，单批最多200条，失败回滚并低频重试。
- 以性能优先，超时处理允许延后数小时；重启、积压或失败可能更久。前端离开不影响后台，实时申诉资格由后端校验。阶段到期但未自动处理时提示等待后台。
- 本版本只提交推送，不部署生产。部署前root核实四项小时数、两级超时策略、日历覆盖、片区范围及终审权限。回退前停止自动任务；降级保留规则、日历、证据，不撤销已发生结论。旧代码使用共享天数语义，不能只回退应用并继续运行后台任务，需另行制定兼容迁移。
- 本地测试：`ISSUE_LIFECYCLE_DB_TEST=1 python -m unittest tests.test_quality_deadlines tests.test_issue_appeals`，数据库测试均在事务内回滚；前端 `node --test tests/*.test.mjs`。
